## 第 7 页：制定 Plan 阶段怎么和 AI 协作
提示词：
生成一页“制定 Plan 阶段怎么和 AI 协作”页面，采用统一四区块结构：目标、AI 负责、我负责、产出。目标写明：把需求变成可执行 Plan。AI 负责：按需求拆分任务、给出任务顺序、识别依赖和风险、提出验证方式，并启动独立子 agent 做 Plan Review。我负责：检查任务拆分是否合理、确认实现顺序、确认是否遗漏边界条件和验收口径。产出：一版经过人工和子 agent 双重审查的 Plan。页面底部放一条结论：“Plan 不是为了写文档，而是为了降低实现阶段返工”。风格专业、简洁、结构清晰。

备注：
这一页讲第二步，也就是制定 Plan。我会先让 AI 根据已经澄清过的需求，把任务拆出来、排好顺序，并把依赖和风险先说出来。然后我自己先审一遍，再额外启动一个独立子 agent，从 review 的视角再检查一次这个 Plan，看看有没有漏任务、顺序不合理或者边界条件没覆盖到。

重点描述：
- 目标：把需求变成可执行 Plan
- AI 负责：拆任务、排顺序、识别风险，并启动子 agent review plan
- 我负责：审核任务拆分、顺序、边界和验收
- 产出：一版经过双重审查的 Plan

## 第 8 页：实现阶段怎么用 AI
提示词：
生成一页“实现阶段怎么用 AI”页面，采用统一四区块结构：目标、AI 负责、我负责、产出。目标写明：按 task 稳定推进并控制改动面。AI 负责：按 task 实现代码、补测试、在边界清晰时并行启动 multi-agent。 我负责：控制任务边界、决定是否并行、判断是否要以 TDD 方式先写测试。产出：每个 task 都有代码结果和可执行验证结果。页面底部放一条结论：“单任务层面更偏向用 TDD / 测试做收口，而不是先做额外 review”。风格专业、简洁、工程化。

备注：
进入实现阶段后，我的默认做法不是一口气让 AI 把整个需求做完，而是按 task 一个一个推进。单个 task 做完之后，我更偏向用 TDD 或自动化测试来做局部收口，而不是再额外开一层 review 流程。只有当子任务边界非常清晰、依赖关系很少、输入输出也明确的时候，我才会考虑开 multi-agent 并行。

重点描述：
- 目标：按 task 稳定推进并控制改动面
- AI 负责：实现代码、补测试，必要时并行启动 multi-agent
- 我负责：控制边界、决定并行、判断是否采用 TDD
- 产出：每个 task 都有代码结果和验证结果

## 第 9 页：Review 阶段怎么用 AI
提示词：
生成一页“Review 阶段怎么用 AI”页面，采用统一四区块结构：目标、AI 负责、我负责、产出。目标写明：在已有验证结果的基础上做总体审查。AI 负责：启动独立 review sub-agent，基于 git diff 检查功能正确性、回归风险、缺失测试、代码异味和不合理改动面。我负责：判断哪些问题是阻塞项、是否需要补测试、是否接受本次改动。产出：一版 review 结论和是否合入的决策。页面明确写出“review 建立在验证结果之上”，风格专业、简洁、结构清晰。

备注：
最后一步是 Review，这一步我会明确启动一个独立的 review sub-agent，基于 git diff 来看这次改动。这里要强调一点，review 不是代替验证，而是建立在前面已经有测试结果和局部验证结果的基础上，再做一次总体审查。最后是不是接受这次改动，还是我自己来拍板。

重点描述：
- 目标：在验证结果之上做总体审查
- AI 负责：启动独立 review sub-agent，基于 git diff 做 review
- 我负责：判断阻塞问题、是否补测、是否接受改动
- 产出：review 结论与是否合入的决策
