# AI Coding 实践分享（大纲 v1）

## 0. 开场（3 min）
- 我是谁 / 为什么做这个分享
- 今天解决的问题：
	- AI Coding 到底能解决什么，不适合解决什么
	- 个人和团队怎样稳定落地，而不是“试玩两天就放弃”
- 今日目标：给大家一套可复制的实践路径

## 1. 背景与结论先行（5 min）
- 为什么现在必须关注 AI Coding
	- 代码生成能力已从“玩具”进入“可用工具”阶段
	- 速度优势来自“反馈回路变短”，不是“替代工程师”
- 结论先行（先讲答案）
	- AI 适合加速：样板代码、重构、测试、文档、排查路径
	- AI 不适合直接接管：核心架构决策、关键业务规则最终拍板
	- 最佳角色定位：AI 是结对编程搭档，不是自动驾驶

## 2. 我的实践场景（5 min）
- 典型工作流（从需求到上线）
	- 理解需求与边界
	- 拆解任务与实现顺序
	- 编码、测试、回归、文档
- 我在哪些环节用 AI（按收益排序）
	- 代码改造与重构建议
	- 单测补全与边界条件提示
	- 读陌生代码、定位问题路径
	- 生成初版文档 / PR 描述

## 3. 一次完整实战示例（15 min，核心）
- 示例背景
	- 任务：一个真实的小需求（可替换为你自己的项目案例）
	- 约束：时间有限、已有历史代码、不能破坏线上行为
- 实战分 5 步
	- Step 1：把需求写成“可执行提示词”
	- Step 2：让 AI 先给方案，不急着写代码
	- Step 3：小步提交代码，持续运行测试
	- Step 4：让 AI 做代码审查与风险扫描
	- Step 5：产出 PR 说明与复盘
- 演示重点
	- 好提示词 vs 坏提示词（对比输出质量）
	- 如何让 AI 在现有代码风格下工作
	- 如何识别“看起来对但实际错”的回答

## 4. 提示词与协作模式（8 min）
- 高质量提示词模板
	- 背景：技术栈、目标文件、约束条件
	- 任务：要改什么，不要改什么
	- 验收：如何判断完成（测试、性能、兼容性）
- 常用指令模式
	- 先解释再改代码
	- 先列风险，再实施变更
	- 先给最小可行改动（MVP patch）
- 与 AI 协作的节奏
	- 需求拆小、回合变短、每轮可验证

## 5. 踩坑与防坑（8 min）
- 常见坑
	- 幻觉：API 存在但实际不存在
	- 过度重构：改动面太大引入回归
	- 忽略业务约束：代码“正确”但业务“错误”
	- 安全与隐私：敏感信息外泄风险
- 防坑清单
	- 每次改动必须可测试、可回滚
	- 关键逻辑必须人工 review
	- 使用“先查文档/源码，再改动”的流程

## 6. 团队落地建议（6 min）
- 三层落地路线
	- 个人层：先在低风险任务建立正反馈
	- 小组层：沉淀提示词模板与评审规范
	- 团队层：定义质量门禁（测试覆盖、lint、review）
- 管理视角关注指标
	- Lead Time、缺陷率、返工率、评审吞吐
	- 不只看“写得快不快”，还要看“改得稳不稳”

## 7. 总结（3 min）
- 三句话总结
	- AI Coding 是效率杠杆，不是责任转移
	- 价值来自“人机协同流程”，不是单次生成质量
	- 小步快跑 + 可验证，是长期有效的方法

## 8. Q&A（7 min）
- 预设问题
	- 会不会替代初中级工程师？
	- 如何评估投入产出比？
	- 哪些场景最值得先试点？

## 附录 A：可直接复用的提示词模板

### 模板 1：需求拆解
你是资深 {{language}} 工程师。请基于以下上下文拆解任务，不要直接写代码。

上下文：
- 项目目标：{{goal}}
- 相关文件：{{files}}
- 约束条件：{{constraints}}

输出要求：
1. 给出 3-5 步最小实现路径
2. 每一步标注风险点与验证方式
3. 给出建议的提交顺序

### 模板 2：最小改动实现
请只修改 {{target_file}}，实现 {{feature}}。

要求：
- 保持现有代码风格
- 不改动无关逻辑
- 给出变更说明
- 补充必要测试

验收：
- {{test_command}} 通过
- 无新增 lint 错误

### 模板 3：代码审查
请对以下改动做 code review，按严重级别输出：
1. 功能正确性
2. 兼容性与回归风险
3. 性能与安全问题
4. 测试覆盖缺口

如果无问题，请明确写“未发现阻塞问题”，并给出建议优化项。
